# Google Drive 실계정 검증

2026-10-19 · Windows x64 · SafeSync C# 백업 엔진

## 1.0.0-preview.1 양방향 추가 검증

최종 백업 코드의 실제 Google 계정 검사 **35개 통과**. 새 `SafeSync-validation-twoway-20261019-013158-817d2657` 폴더에서 최초 양방향 합집합, 원본/원격 수정, 양쪽 삭제와 휴지통, 동시 수정 충돌 중 다른 파일 계속 처리, 백업→원본/원본→백업 선택, 삭제+수정 충돌, 재시작 스냅샷·커서 승계, 빈 폴더와 중첩 파일을 확인했다. 기존 계정 설정 SHA-256은 검사 전후 일치한다.

변경 없는 비교 3.657초, 커서가 유지된 재시작 비교 4.286초였다. 작은 시험 폴더에서의 관측이며 대량 파일 성능 보장은 아니다. 원본의 안전 재확인이 원격 전체 열거를 강제하지 않는 것을 확인했다.

결과: `artifacts/tests/safesync-v2-33ec6a6cfb104806bea9871d78c3b3a1/google-two-way-result.json`. 테스트 폴더만 변경했고 기존 백업은 건드리지 않았다. 아래는 이전 단방향/재시작 시험 기록이다.

## 격리 및 인증

사용자가 연결해 둔 `SafeSync2-Preview`의 Google 계정을 읽기 전용으로
사용했다. 토큰 갱신과 실제 계정/Drive 루트 접근이 통과했다. 계정 설정은
메모리에서만 사용했고 테스트 설정/보고서에 인증 정보를 복사하지 않았다.
기존 작업과 백업 폴더는 실행/변경하지 않았다.

원본 자료는 로컬 `artifacts/tests/safesync-v2-*/google-live-source`에
생성했다. 클라우드는 내 드라이브에 새로 만든 `SafeSync-validation-*`
폴더만 사용했으며, 변경 작업은 그 폴더 ID에 고정한 어댑터로 제한했다.
기존 계정 설정 파일의 검사 전후 SHA-256 일치도 확인한다.

## 기본 실계정 시나리오

첫 실계정 실행은 **52개 검사 통과**했다.

- 14개 초기 파일: 작은 파일, 빈 파일, 한글/이모지 경로, 16 MiB+123바이트 파일
- 원격 서비스 체크섬 검증 및 실제 다운로드 후 SHA-256 비교
- 생성/수정 시간 보존, 스냅샷/Google Changes 커서 저장
- 새 엔진에서 스냅샷 재사용, 변경 없는 파일 재업로드 없음
- 변경된 파일만 교체하고 이전 파일은 SafeSync 휴지통에 보관
- 시간은 같지만 크기가 다른 충돌을 만들고 다른 파일은 계속 백업
- 이번 실행 무시 / 기존 파일 이름 변경 후 원본 복사
- 사용 중인 파일은 일반 오류 대신 대기, 잠금 해제 후 대기 해소
- 원본 삭제 → 백업 휴지통 이동 → 원래 파일 ID/내용으로 복구
- 100일이 지난 시험용 휴지통 배치 정리, 선택한 시험 휴지통 파일 삭제
- 일시정지/재개, 중단 전송의 대기 스냅샷/저널 보존과 복구

응답 유실 시험에서는 실제 Google 서버가 첫 8 MiB를 받은 뒤 **검사 전용
HTTP 클라이언트에서만** 그 응답을 버렸다. 새 엔진/원격 저장소에서 서버의
전송 위치를 조회하고, 다음 조각을 8 MiB 위치부터 보냈다. 전송 조각 시작
위치가 `[0, 8388608]`이고 복구 파일의 다운로드 SHA-256이 원본과 같음을
확인했다. 네트워크 장비를 끊거나 실제 사용 중인 앱을 종료한 시험은 아니다.

## 발견하고 수정한 재시작 조회 문제

원본의 변경 기록이 없어 전체 원본 재확인이 필요할 때, 동일한 `full` 값을
Google 인덱스 갱신에도 전달하여 **유효한 원격 커서가 있어도** 폴더 트리를
다시 열거했다. 실제 계정의 17개 파일로 재현했다. 복사는 성공했지만 불필요한
전체 목록 조회가 발생했다.

preview.9에서는 원본 재확인과 원격 전체 조회를 분리했다. 수동 전체 비교는
두 위치를 다시 확인하며, 원격 커서 누락/만료 또는 계정/루트 변경은 기존처럼
안전하게 원격 인덱스를 다시 구성한다. 원본 변경 기록 손실에 대한 안전 확인을
제거한 것이 아니다.

| 실제 재시작 경로 | 수정 전 | 수정 후 1회 | 수정 후 2회 |
| --- | ---: | ---: | ---: |
| 원본 재확인 | 수행 | 수행 | 수행 |
| 백업 폴더 전체 열거 | 3회 | 0회 | 0회 |
| HTTP 요청 | 23회 | 11회 | 11회 |
| 소요 시간 | 7.428초 | 4.020초 | 4.038초 |
| 파일 재업로드 / 오류 | 0 / 0 | 0 / 0 | 0 / 0 |

수정 후는 매번 새 HTTP 클라이언트/계정 서비스/백업 엔진을 만들고 실제 시작과
같은 `reconcileOffline=true`로 실행했다. 총 **6개 실계정 재시작 검사**가 통과했다.
첫 회에는 시험 스냅샷의 원본 재확인 플래그를 명시적으로 켰다. 이 수치는 소규모
단일 환경의 측정으로 대규모 데이터의 속도 개선 배율을 보장하지 않는다.

수정 전 증거:
`artifacts/tests/safesync-v2-c8cc91dd564d457aa5659379fbece91c/google-recheck.json`

수정 후 증거:
`artifacts/tests/safesync-v2-10d9dd55008247959a668af22706263c/google-recheck.json`

합성 회귀 검사도 추가했다. 원본 재확인 시 새 원본 파일과 원격 변경 피드가
함께 반영되고, 수동 전체 비교/커서 만료는 계속 원격 전체 조회를 수행한다.

## 최종 수정본 재검사

preview.9의 전체 실계정 시나리오를 두 번째 새 폴더에서 다시 실행하여
**52개 모두 재통과**했다. 계정 설정 해시는 그대로이며, 전송 재개 시 첫 조각을
다시 보내지 않고 8 MiB 위치부터 이어 보냈다.

최종 실행 증거:
`artifacts/tests/safesync-v2-9a12d985818f48ffadbb299f56fa0ad4/google-live-result.json`

[최종 수정본 검사 폴더](https://drive.google.com/drive/folders/1QzKvEXpQjtUuT9bbNU5tsAeLBL1cYvNV)

앞선 첫 검사 폴더와 최종 검사 폴더 모두 남겨 두었다. 만료/선택 삭제 시험은
이 폴더 안에서 생성한 시험용 휴지통 항목만 대상으로 했으며, 기존 백업이나
사용자 휴지통 항목은 삭제하지 않았다.

최종 실행에서 최초 14개 파일 백업은 101.717초, 직후 변경 기록을 소비하는
무변경 비교는 17.258초, 한 파일의 증분 교체는 18.146초였다. 위 재시작 표는
변경 기록이 정리된 17개 파일에서의 별도 측정이다. 최초 전송과 개별 교체에는
여전히 여러 메타데이터/안전 확인 요청이 발생하므로 추가 최적화 여지가 있다.
이번 수정으로 업로드 전반이 두 배 빨라졌다고 주장하지 않는다.

## 남은 범위

새 브라우저 로그인/동의 화면, 공유 드라이브/조직 정책, 권한 취소, 실제 서비스의
요청 제한, 저장 공간 소진, 물리적 네트워크 단절·전원 장애, 수 GB 이상 파일과
며칠간의 연속 실행은 이 검사로 검증했다고 표시하지 않는다. Dropbox 실계정도
별도 검사 대상이다. 데이터와 복구 사본은 확인할 수 있도록 테스트 폴더에 보존했다.
