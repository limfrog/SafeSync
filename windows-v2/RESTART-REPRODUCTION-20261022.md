# Windows 재시작 동기화 재현 검사

2026-10-22 · Horizon Entertainment · apps@horizonent.co.kr

## 결론

현재 Windows preview.14의 동기화 본체를 변경하지 않고 GitHub의 독립 Windows Server 2022/2025 환경에서 재시작 문제를 재현했다. **검사는 실패이며, 현재 동작을 ‘오류 없이 의도대로 작동’한다고 판단할 수 없다.** 데이터 재복사와 전체 재비교는 별개다. 변경 없는 파일 재복사는 0개였지만, 단방향에서는 257개 파일 모두를 다시 내용 검증했고 폴더 8개가 잘못된 충돌로 남았다.

## 환경과 재현 방식

- 제품 소스 기준: `bfca3da53ce5bc81e02fe2c538e3277f33c0cb14` (Windows `1.0.0-preview.14`). 테스트 추가 후에도 `windows-v2/src/`와 `Directory.Build.props`는 기준과 동일하다.
- 최초 실행: [GitHub Actions 39630010865](https://github.com/limfrog/SafeSync/actions/runs/39630010865), 검사 커밋 `62ba0f0a8ade93a39f892437b3880b7db18ea014`.
- 두 서버 환경 각각 새 NTFS 가상 디스크·USN 변경 저널·임시 localhost SMB 공유를 준비했다. 기존 사용자 설정·토큰·실제 백업은 사용하지 않았다.
- 각 작업에 폴더 8개, 작은 파일 256개, 4 MiB 파일 1개를 만들었다. NTFS 단방향/양방향, SMB 원본 단방향, SMB 백업 단방향/양방향을 검사했다.
- 매번 실제 자식 프로세스를 종료하고 새 프로세스에서 제품의 `BackupScheduler.SetJobs` → `Start` 자동 실행 경로를 사용했다. 변경 경로 목록을 주입하지 않았다.
- 검사 대상은 제품의 Core·실행 관리자이며 WPF 화면 시작/종료 자체를 조작한 것은 아니다.

## 최초 실행 결과

각 OS에서 82개 정확성 검사 중 64개 통과, 18개 실패. 기존 격리 회귀 검사 1,004개는 각 OS에서 모두 통과했다. 기존 검사의 통과는 아래 재현 실패를 상쇄하지 않는다.

변경 없는 두 번째 재시작 결과는 두 OS에서 다음과 같이 동일했다.

| 구성 | 전체 비교 | 비교 경로 수 | 단방향 명시적 내용 검증 파일 수 | 복사 | 충돌 | 남은 대기 경로 |
|---|---|---:|---:|---:|---:|---:|
| NTFS 단방향 | 원본 전체 | 265 | 257 | 0 | 8 | 8 |
| NTFS 양방향 | 양쪽 전체 | 265 | 별도 계측 없음 | 0 | 0 | 0 |
| SMB 원본 단방향 | 원본 전체 | 265 | 257 | 0 | 8 | 8 |
| SMB 백업 단방향 | 원본 전체 | 265 | 257 | 0 | 8 | 8 |
| SMB 백업 양방향 | 양쪽 전체 | 265 | 별도 계측 없음 | 0 | 0 | 0 |

265개 경로는 파일 257개와 폴더 8개다. 양방향의 내용 검증 항목이 별도 계측되지 않았다는 것은 해시 읽기가 없었다는 뜻이 아니다. 모든 변경 없는 검사에서 실제 복사/삭제는 0개였고, 백업 파일 내용·파일 식별자·수정 시각 보존 검사는 통과했다. 각 OS의 기록된 33회 실행 모두 원본 전체 비교 단계가 있었다.

### 발견 1: 로컬 NTFS 변경 저널 조회 실패

`OfflineJournal.Read`가 볼륨을 현재 제품의 접근 플래그 `0`으로 열면 저널 조회가 두 OS 모두 Windows 오류 `1`로 실패했다. 스냅샷의 저널 체크포인트는 `null`로 남았고, 시작 시 `RequiresScan=true` 조건으로 전체 비교가 실행됐다.

같은 테스트 볼륨을 별도의 읽기 전용 진단 핸들에서 `GENERIC_READ`로 열었을 때는 저널 조회와 읽기가 모두 성공했으며 레코드 버전도 2였다. 따라서 이 시험에서는 ‘변경 저널 자체가 없는 볼륨’이 아니라 **제품의 볼륨 접근 방식에 따라 조회가 실패하는 현상**을 확인했다.

이 진단은 제품의 핸들·권한·로직을 바꾸지 않았다. 서버 실행 환경의 권한에서 확인한 것이므로, 실제 수정 시에는 일반 사용자 권한과 Windows 10/11에서도 검증해야 한다. 앱 전체를 관리자 실행으로 강제하는 것으로 해결했다고 간주하지 않는다.

관련 코드: `src/SafeSync.Core/OfflineJournal.cs`, `BackupScheduler.cs`, `BackupEngine.cs`, `TwoWayEngine.cs`.

### 발견 2: 폴더 변경 이벤트가 단방향 파일 처리에 들어가 잘못된 충돌 생성

초기 복사 때 발생한 폴더 이벤트가 변경 대기열에 남는다. `ChangePlanner.Add`는 폴더 자체도 파일 작업 대기열에 넣는다. 단방향 엔진은 이를 `FileInfo`로 검사해 파일이 없는 것으로 처리하고, 실제 폴더가 존재하는데도 삭제 검증 경로에 진입한다.

그 결과 첫 재시작부터 `folder-00`~`folder-07` 8개가 충돌로 저장됐다. 이후에는 ‘이전 버전의 원본 확인 정보가 없어 삭제를 반영하지 않았습니다’라는 메시지로 다시 남았다. 이 검사는 이전 버전에서 가져온 작업이 아니라 완전히 새 작업이므로, 이 메시지는 실제 원인을 설명하지 못한다.

관련 코드: `src/SafeSync.Core/ChangePlanner.cs`, `BackupEngine.cs`, `OneWayRoots.cs`.

### 통과한 안전 검사

- 변경 없는 백업의 내용·식별자·수정 시각 보존.
- 양방향에서 프로그램 종료 중 양쪽 파일 변경 및 삭제 전파와 휴지통 보존.
- 크기·생성/수정 시각을 같게 유지한 내용 변경을 동기화하거나 명시적 충돌로 보존.
- 40개 파일 중 5개 완료 후 제품 체크포인트 저장 지점에서 테스트 프로세스를 실제 강제 종료. 파일 5개와 대기 35개 기록이 남았고, 새 프로세스에서 나머지 35개를 완료했다. 완료된 5개 사본은 재교체되지 않았다.

최초 검사에서 단방향 종료 중 변경 검사는 ‘무충돌 상태와 파일 내용 일치’를 한 조건으로 검사했으므로 폴더 충돌 때문에 실패했다. 이를 ‘파일 변경을 놓쳤다’고 단정하지 않는다. 아래 후속 진단에서 두 결과를 분리해 확인했다.

## 최종 재검사: 상태와 파일 내용의 분리 검증

[GitHub Actions 39631271548](https://github.com/limfrog/SafeSync/actions/runs/39631271548), 검사 커밋 `46783d21c61e7e3d530df6853346c145ddb2c487`. 제품 Core는 처음과 동일하고, 테스트에서만 모든 실행 직후 양쪽 전체 파일 목록·길이·SHA-256·식별자·수정 시각을 기록하고 충돌 사유를 추가했다. 첫 검사에서 발견한 실패를 무시하거나 합격 조건을 완화하지 않았다.

- **각 OS에서 89개 중 71개 통과, 18개 실패**. 첫 검사의 18개 실패가 동일하게 재현됐다.
- 각 OS에서 종료 중 원본 변경 5개 구성과 백업 쪽 변경 2개 구성, 총 7개 내용 일치 검사가 모두 통과했다. 양쪽 파일 목록과 SHA-256이 일치했다. 단방향도 실제 파일 변경은 반영됐지만 폴더 충돌 8개가 남아 작업 상태는 정상 완료되지 않았다.
- 변경 없는 재시작에서 복사 합계는 각 OS 모두 **0개**. 백업 내용·식별자·수정 시각 보존 검사는 계속 통과했다.
- NTFS 변경 저널 조회 실패와 폴더 8개의 잘못된 충돌, 반복 전체 비교가 두 OS 모두 동일했다.
- 저장된 체크포인트에서 강제 종료 후 남은 파일 35개를 복구하고, 완료된 5개 사본을 유지하는 검사가 계속 통과했다.
- 기존 회귀 검사 **1,004개도 각 OS에서 다시 통과**했다. 그럼에도 새 재현 검사는 실패 상태다.

따라서 이 범위에서 확인된 현상은 ‘모든 파일을 반복 복사’ 또는 ‘종료 중 변경을 누락’이 아니라 **전체 비교·내용 읽기 반복과 잘못된 폴더 충돌로 미완료 상태가 지속되는 결함**이다. 이 결론을 실제 Google Drive/NAS의 모든 증상이나 모든 종류의 파일 손상 부재로 확대하지 않는다.

최종 보고서 ZIP SHA-256:

- Windows 2022: `604373180ba84a1a6e9ed0ce1e0f2ba7a92053facfc07c459773d30a89b0802b`.
- Windows 2025: `a4949ed065a6851fb328886a8f00e4ad502f50a562b9603a32fd5fae2466f783`.

각 실행의 `*.inventory.json`은 테스트 자료의 전체 파일별 결과를 담는다. 이 ZIP은 GitHub가 제공한 다이제스트와 일치함을 내려받은 파일에서도 확인했다. 실제 재현은 GitHub에서 실행했고, 사용자 PC에서는 검사 프로그램 컴파일과 합성 결과 보고서 열람만 수행했다. 사용자 실행 앱을 종료하거나 실제 작업을 실행하지 않았다.

## 범위와 후속 순서

실제 NAS/Samba, Google Drive/Dropbox 계정, Windows 10/11 사용자 화면, 컴퓨터 재부팅, 파일 전송 도중 전원 차단은 검사하지 않았다. localhost SMB는 실제 NAS의 완전한 대체가 아니다. 강제 종료는 파일 사이의 저장된 체크포인트에서 실행했으며 개별 파일 전송 도중의 강제 종료 검사가 아니다.

이번 작업은 **재현·진단만** 수행한다. 제품 동기화 판단, 설치본, 버전, 업데이트 목록, 홈페이지는 바꾸지 않았다. 우선 두 결함을 수정하고 동일 검사로 재검증한 뒤, NAS 감시 공백에서 필요한 재검사 범위를 별도로 최적화하는 것이 적절하다.
