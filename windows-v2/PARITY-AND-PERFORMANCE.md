## 7일 기준 제거

시간이 일주일·한 달 지났다는 이유만으로 전체 비교하지 않는다. 첫 백업, 수동 전체 검사, 손상/불일치 스냅샷, 감시 누락/재연결, 유실·미지원 변경 기록은 안전한 재확인을 할 수 있다. 이는 모든 파일의 무조건 재전송과 다르다. 정상 파일은 메타데이터 비교 후 건너뛴다.

구버전 설정을 가져온 직후 한 번의 재확인은 유지한다. 구버전의 미완료 전송은 구버전에서 복구 후 가져와야 하며, 신버전이 임의 재생하지 않는다.

## 의도적으로 보존한 안전 차이

삭제 반영을 켜도 신버전은 스냅샷에 추적된 백업 파일만 휴지통으로 옮긴다. 백업 위치에 사용자가 따로 넣은 미등록 파일까지 자동 정리하도록 확대하지 않았다. 더 공격적인 완전 미러링은 별도 동의 옵션과 시험이 필요하다.

이번 작업은 코드/검증 ZIP을 만든 것이며 실제 계정, 백업 자료, 레지스트리, 기존 설치본 및 GitHub 릴리스를 변경하지 않는다. 사용자가 새 앱의 환경설정을 저장하면 그때 자동 시작 등록이 적용된다. 수동으로 등록한 구버전 자동 시작은 직접 확인해야 한다.

## 추가 성능 아이디어 (미적용)

1. **SQLite 기반 파일/경로 인덱스**: 전체 JSON 로딩·시작/종료 전체 스냅샷 정리 비용을 줄인다. 가져오기/롤백/DB 손상 복구를 포함해 별도 검증해야 한다.
2. **폴더 ID/세대 검증 캐시**: Drive 경로를 구성하는 부모 폴더의 반복 조회를 줄인다. 변경 피드로 무효화하고 교체 직전에는 실제 대상을 다시 확인해야 한다.
3. **환경별 적응형 동시 전송**: 작은 파일에서 2→4개를 시험하되 API 제한/응답 지연/메모리 사용에 따라 낮춘다. HDD·NAS에서는 과도한 병렬 읽기를 피한다.
4. **계측 기반 병목 표시**: 비교·로컬 안정 사본·체크섬·API 대기·업로드·교체 시간을 별도 기록하여 사용자의 실제 NAS/Drive에서 우선순위를 정한다.
5. **진행 이벤트 묶음 갱신**: 파일마다 UI를 다시 그리는 대신 작업별 최신 진행을 100~200ms 간격으로 반영하여 대량 비교 때 UI 대기열 부담을 줄인다.

설계 근거: [SQLite 인덱스/쿼리 계획](https://www.sqlite.org/queryplanner.html), [WPF 스레딩과 UI 응답성](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model), [Google Drive 성능·배치 가이드](https://developers.google.com/workspace/drive/api/guides/performance).

실제 네트워크 백업 속도가 몇 배 빨라진다고 단정하지 않는다. 자동 검사는 합성 파일/모사 API의 기능·요청 수·체크포인트 크기를 확인하며 실제 Drive/Dropbox/NAS 처리량 측정을 대신하지 않는다. Windows USN 접근 권한/파일시스템별 성공 여부도 실제 환경에서 확인해야 한다.
